我建议不要把现有的国家级网站适配方案，简单复制成多个省、市、区县网站的适配方案。那样短期能接入几个网站，但后面每增加一个地方站点，都可能需要改代码、改解析规则、改 AI 提取提示词，维护成本会越来越高。

更合理的升级方向是：从“国家级网站适配”升级为“多层级、可配置、可持续扩展的网站接入体系”。

你现有方案其实已经有一个很好的基础：把数据源作为插件，并将检索、正文获取、清洗、入库判别、结构化提取抽象成一条完整链路。

落地方案设计.md

&#x20;现在要解决的，是如何把这个原则落到多地方网站的工程架构上。

## 一、先明确：地方网站扩展，究竟难在哪里？

国家级网站和地方级网站的差异，并不只是域名不同，而是网站结构、信息组织方式和内容质量都可能不同。

1\. 网站入口不同

有的网站提供统一检索，有的网站按栏目浏览，有的网站只有信息列表；部分内容还分散在部门子站。

2\. 页面和文件结构不同

可能涉及不同的 CMS 模板、动态页面、分页规则、PDF 附件、正文和附件分离等情况。

3\. 内容语义和质量不同

同一类政策，在不同地区可能使用不同栏目名称、文种和元数据字段；地方转载、重复发布、附件缺失等问题也需要单独处理。

4\. AI 的提取结果需要统一治理

即使不同网站都能抓到正文，提取出的发布日期、生效日期、发文机构、适用区域等字段仍可能不一致，也需要统一验证。

因此，不能只做一个“地方网站爬虫模块”。真正需要拆开的，是网站接入、内容处理、事实提取与核验、来源治理这几个不同层次。

## 二、目标架构：从单站适配升级为“通用引擎 + 网站适配器 + 来源策略”

我建议采用三层接入架构，再复用之前讨论过的事实提取和知识生产流水线。

第一层 · 统一管理

来源注册与接入配置中心

登记国家 / 省 / 市 / 区县、机构、网站、栏目、来源可信等级、采集频率、许可和负责人。

第二层 · 网站接入

可复用的网站适配器

检索适配器

搜索接口、栏目列表、RSS、API

抓取适配器

HTML、动态页面、附件下载

解析适配器

页面正文、元数据、PDF 和附件

网站专属规则

分页、字段映射、清洗和异常处理

第三层 · 统一知识生产流水线

原始证据 → 事实候选 → 事实核验 → 信息聚合 → 知识候选 → 人工审核与发布

无论接入的是国家级网站还是地方网站，经过适配后都进入同一条业务主链。

这套架构的关键，是将“网站怎么接入”和“接入的内容怎么生产知识”分离。

以后新增一个地方网站，原则上只需要注册来源、选择适配器、配置差异规则。只有遇到现有能力无法覆盖的网站，才需要开发新的适配器或解析插件。

## 三、不同地方网站，不应该采用同一种适配方式

建议将现有国家级网站和待扩展的地方网站进行归类，而不是按省份直接划分开发任务。

| 网站类型                        | 推荐接入方式               | 是否需要单独开发              |
| ------------------------------- | -------------------------- | ----------------------------- |
| 提供开放 API 或结构化数据的网站 | API 适配器                 | 通常只需配置接口与字段映射    |
| 使用相似 CMS 模板的网站         | 通用列表、详情页解析器     | 通常配置栏目和选择器即可      |
| 结构差异较大的网站              | 可插拔的专属解析器         | 需要少量定制开发              |
| 采用复杂动态交互的网站          | 浏览器渲染或专用采集适配器 | 视动态逻辑而定                |
| 主要以 PDF、附件发布内容的网站  | 文档下载与解析适配器       | 需要适配文档类型和 OCR 等能力 |

这些类型并不是互斥的。一家地方政府门户网站可能同时使用列表页、动态页面和 PDF 附件。

尤其需要避免一种设计：把国家级网站当前使用的页面选择器、分页逻辑和字段规则直接写进通用采集引擎。 这样会把原本只适用于特定网站的假设传播到所有新来源。

## 四、具体应该把什么做成配置，什么保留为代码？

这是整个改造最关键的工程决策。

建议把每个网站的差异抽象成一份“来源接入配置”。例如：

```
source:
  id: local_gov_example
  name: 某地方政府门户
  level: city
  organization: 某市人民政府
  source_type: official_government

  adapter:
    discovery: html_list
    fetch: http
    parser: government_portal_v1

  scope:
    start_urls:
      - "https://example.gov.cn/zwgk/"
    allowed_domains:
      - "example.gov.cn"

  rules:
    list_pagination: query_parameter
    detail_selector: "article"
    title_selector: "h1"
    date_selector: ".publish-date"
    attachment_selector: "a[href$='.pdf']"

  extraction:
    profile: policy_document_v1

  schedule:
    interval: daily

  governance:
    require_original_evidence: true
    review_required: true
```

以上只是配置结构示例，并非已经验证过的某个真实政府网站配置。实际选择器、分页方式和访问规则必须根据目标网站的真实结构确认。

### 建议采用四种不同的扩展机制

1\. 参数配置

域名、栏目入口、采集时间范围、更新频率、条数上限、允许访问的路径等。

2\. 适配器组合

从已有的 HTML、API、RSS、PDF 等能力中组合接入流程，不必为每个网站复制一套完整代码。

3\. 网站专属插件

处理特殊分页、特殊编码、动态渲染或不规则附件等通用组件难以覆盖的情况。

4\. 内容提取策略

依据内容类型选择政策、通知公告、地方规章、政府工作报告等不同的提取模板，而不是每接入一个网站就重新发明一套 AI 提取逻辑。

其中，代码插件应当有统一接口、版本和测试规范；不能让配置随意执行未经审核的代码，也不能把任意 URL 直接交给爬虫执行。来源域名、网络访问范围、访问频率和重试策略都需要受控。

## 五、接入地方网站后，AI 事实提取应该怎么处理？

这部分需要与前面讨论的“AI 提取结果不是原始证据”保持一致。

我建议把网站差异和内容差异分开处理：

网站接入层负责回答：

- 这是什么网站、哪个机构发布的？
- 如何发现内容、下载原文、定位正文和附件？
- 网站提供了哪些原始元数据？
- 如何稳定获取并保存原始材料？

AI 提取层负责回答：

- 这份材料是什么文种、属于什么主题？
- 哪些字段和事实可以从原文中提取？
- 每条事实对应原文中的什么位置？
- 哪些字段缺失、存在歧义或与其他来源冲突？

举例而言，不同地方网站的日期字段可能叫“发布日期”“成文日期”“印发日期”。采集器应尽可能保留源站的原始字段和文本，而不是直接把它们全部映射为同一个“日期”。

随后，AI 或规则层识别日期的语义，将结果结构化为：

```
发布机构：某市人民政府
发布日期：2026-03-10
成文日期：2026-03-08
事实候选：该政策自 2026-04-01 起施行

证据来源：原始文件
证据位置：正文对应段落
核验状态：待核验
```

这里的日期仅用于示例。发布机构、发布日期、成文日期、生效日期等字段必须分别保存，不能因为来源网站的字段名称不同就混淆其语义。

因此，AI 提取最好按内容类型选择提取模板，网站配置只负责提供必要的来源信息和原文定位能力。当确实存在地方特有的业务字段时，再通过可扩展字段补充，不应让每个网站都产生完全不同的事实数据结构。

## 六、从当前国家级网站适配，如何分阶段升级？

不建议一开始就覆盖所有省、市、区县网站。更稳妥的方式是先验证适配器能否复用，再扩大来源范围。

1. 第一阶段：拆解现有国家级适配器

   盘点当前代码中的检索、抓取、正文解析、附件处理、元数据映射和 AI 提取规则。将通用能力抽离为公共组件，将国家级网站专属规则转为配置或插件。

2. 第二阶段：选择代表性的地方网站试点

   优先选择结构化程度较高的网站，再挑选使用不同 CMS、不同分页方式、带 PDF 附件的站点。试点目标不是一次接入很多网站，而是验证同一套引擎能覆盖多少不同模式。

3. 第三阶段：建立网站接入验收机制

   每个新网站都要验证正文完整率、元数据准确率、附件解析率、重复记录识别率、事实原文对齐率、增量更新效果和异常恢复能力。不能只以“页面抓取成功”作为接入完成的标准。

4. 第四阶段：形成来源模板库

   把试点验证成功的配置和插件沉淀下来，新的网站优先匹配既有模板；只有无法适配的部分才新增开发。

5. 第五阶段：扩展为持续运营的来源治理体系

   增加网站健康检查、页面结构变化检测、采集任务监控、失败告警、配置版本管理和重新处理能力。网站改版时只修复受影响的接入组件，再按需重跑下游处理。

## 七、最终需要判断的是：新增网站的边际成本能否下降

建议关注三个指标：

- 配置接入率：新增网站中，有多少能通过已有适配器和配置接入。
- 定制开发率：有多少网站必须编写专属代码，以及原因集中在哪些能力缺口。
- 维护与质量指标：网站结构变化后的故障恢复时间，以及正文和事实提取质量是否达到要求。

如果每接一个地方网站都要重新开发采集器、重新编写整套提取逻辑，那么即使系统名义上支持多个网站，也还没有真正完成平台化。

反之，如果相似网站可以复用模板，差异网站可以增加独立插件，所有内容又进入统一的证据、事实、信息、知识流水线，这套架构才具备真正的规模化扩展能力。

我最建议你下一步先做的，不是马上接入几十个地方网站，而是把当前国家级网站适配拆解成一张“通用能力清单 + 国家级专属规则清单”。 这张清单能够直接决定哪些代码需要抽象、哪些规则应该配置化，以及第一个地方网站试点该选什么类型。
