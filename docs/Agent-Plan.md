核心需求不单是“爬到一个页面后提取正文”，而是让 Agent **像用户一样使用政策网站：选择来源，搜索、分类、筛选、翻页，找到目标文件，再提取标题、日期、文号、机关和正文，最后交给 Agent 加工入库**。如果用户不指定来源，还希望它能先自行发现来源，再走这套流程。

**能实现，但关键不只是正文抽取器，而是要让 Agent 有能力操作搜索入口和结果页。** 它需要一组能搜索、筛选、翻页、进入详情页、提取内容并核验来源的工具。

## Agent 需要哪些工具

### 1. 来源发现与搜索工具

用户指定“中国政府网政策文件库”时，直接把搜索请求交给该库的适配器；未指定来源时，先通过搜索工具发现候选页面或来源，再逐个判断是否值得检索。

搜索能力最好支持这些条件：

- 关键词、地区层级、来源类别
- 发布时间范围、文件类型、分类
- 页码、每页条数
- 来源域名或指定站点

搜索来源可以是网站提供的公开 API、站内搜索接口，也可以是通用网页搜索服务。搜索服务负责**发现候选内容**；它不一定能代替 Agent 进入网站后继续操作站点内的分类、筛选和分页。

### 2. 网站交互工具

当目标站点的搜索结果或筛选条件只能通过网页操作获得时，Agent 需要浏览器自动化能力，例如 Playwright：

- 打开搜索/列表页
- 填写关键词和日期
- 选择分类或地区
- 点击搜索、下一页和详情链接
- 读取页面状态和结果

不同网站的页面结构和控件不一致，所以不能保证“给 Agent 一个浏览器，就能自动理解所有网站”。浏览器适合做**通用交互兜底**；对重点站点，如果确认有稳定的 API 或固定页面模式，应优先走专用连接器，通常更快、更稳定。

### 3. 页面抓取与内容抽取工具

从详情页获取原始页面后，再抽取统一字段：

```text
title, date, document_number, issuing_agency, category,
region, body, source_url, retrieved_at
```

抽取可以分层进行：

1. 网站专用字段映射；
2. 通用正文提取器和 HTML 结构识别；
3. 必要时让模型从**已抓到的页面内容**补齐字段，并保留原文依据；
4. 仍无法确认的字段标记缺失或低置信度。

PDF、扫描件等需要独立的文本提取或 OCR 流程。Agent 不应把“页面上没提取到”当成“原文没有”。

### 4. 结果筛选与分页工具

Agent 得到一页搜索结果后，需要能继续操作结果集：翻页、按日期或类别筛选、去重、限制条数，并在满足条件时停止。这个能力可以由网站适配器提供，也可以由 Agent 在多个 MCP 工具调用之间编排，但不能只依靠一次搜索调用。

### 5. 来源与结果核验工具

每条结果最好带回来源 URL、站点名称、抓取时间、页面日期和字段置信度。可再加一个核验步骤，确认：

- 页面是否对应目标标题；
- 发布日期和文号是否来自页面原文；
- 提取的正文是否过短、混入大量导航内容，或疑似不完整；
- 多个候选页面是否是重复转载。

这对后续 Agent 做政策摘要、对比或引用尤其重要。

## Agent 实际上的工作流程

用户请求“查某地近半年有关某主题的政策”时，Agent 可按以下顺序工作：

```text
理解条件
  → 选择官方政策库适配器，或发现候选站点
  → 提交关键词、地区、日期、类别等筛选条件
  → 查看结果并按需翻页、收窄条件
  → 进入匹配的详情页
  → 提取标题、日期、文号、机关、正文和来源
  → 检查提取完整性，必要时重新抽取或核验
  → 将有来源依据的内容交给 Agent 加工
```

这可以由一个 Agent 顺序调用工具完成；初期**不需要多 Agent**。把搜索、浏览器交互、正文抽取做成清晰的工具接口，比拆成多个 Agent 更容易控制和测试。

## 推荐的工具组合

| 工具 | 推荐用途 |
|---|---|
| **官方站点连接器** | 对中国政府网政策文件库等重点站点，直接封装它的搜索、分类、筛选和分页能力 |
| **浏览器自动化** | 页面没有可用接口，或筛选、翻页等，需要通过通过网页操作作为兜底 | 
| **通用网页搜索** | 用户未指定来源时发现候选页面和来源 |
| **通用正文抽取器** | 从详情页抽取正文、标题和常见元数据 |
| **PDF/OCR 提取器** | 处理 PDF 和扫描文件 |（先不做）
| **结构化解析与核验** | 统一字段、保留证据，检查提取是否可信 | 

## 如何利用现有项目

可以复用现有实现，但它们覆盖的是不同环节：

- `getLatestPolicies.ts` 有中央政策库检索逻辑，可以作为“官方站点连接器”的起点；要满足你描述的完整用法，需要确认并补齐分类、筛选和分页行为。
- `clients.py` 已有通用页面抓取、正文抽取和发布日期处理，可作为详情页抽取层的起点。
- `verify.py` 有候选来源筛选和内容核验的思路，可参考它如何根据页面内容判断是否匹配目标。

## 最重要的设计选择

建议把能力拆成两种模式，而不是追求一个“万能接口”：

- **站点模式**：目标来源明确且有可用搜索入口时，调用该站点连接器，精确执行搜索、筛选、分页。
- **发现模式**：用户没有指定来源时，先用搜索服务找到候选来源，再逐个抓取和核验；必要时用浏览器操作候选站点。

这样，中央、省、市、区县网站都可以逐步纳入，而不用一开始就为所有网站手写解析器，也不会误以为通用搜索能替代每个站点自己的分类和筛选界面。初期最适合先做“中央政策库连接器 + 通用网页搜索 + 通用详情页提取 + 浏览器兜底”，再用实际查询结果补充高价值的地方站点连接器。

需要接受一个边界：**Agent 可以尝试操作未适配的网站，但无法保证任意网站的筛选控件都能被正确识别，或搜索引擎一定收录区县站点。** 因此应在结果中明确返回来源、命中条件、提取状态和不确定项，而不是把“没查到”说成“没有相关政策”。
