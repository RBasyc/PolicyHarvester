# A. Chat agent (`app/agent/`)

> Part of the [docs wiki](../README.md). Companion pages: [overview.md](overview.md),
> [data-pipeline.md](data-pipeline.md), [source-onboarding.md](source-onboarding.md).

The ReAct graph: `START -> agent --(tool calls)--> tools`, looping until the model stops
calling tools. Key flows that span multiple files:

- **Optional browsing** (`app/browser/`, Phase 24): whenever the engine is available
  (`BROWSER_ENABLED=true` and playwright importable) each chat request creates a per-request
  `BrowserRun`, puts it in the `browser_run_var` ContextVar, and the model may call
  `browser_*` tools — there is no per-turn toggle (removed 2026-10-22; unused runs are cheap
  because the session opens lazily). `all_tools()` always contains them (ToolNode must be able to execute),
  but `call_model` filters the list before `bind_tools` — without an active run the schemas
  never reach the model. `prompts/chat_browser.md` is appended only in that mode. See
  [browser.md](browser.md) for the security invariants and the worker-loop design; this page
  only covers the chat-side wiring.

- **Tool registration is a two-stage registry** (`app/agent/tools.py`): local `@tool` functions live in `TOOLS`; MCP tools are appended to `MCP_TOOLS` at startup. Both `graph.py` (ToolNode) and `nodes.py` (`bind_tools`) call `all_tools()`, so the chat graph **must be compiled after MCP tools load** — enforced by the FastAPI `lifespan` in `app/main.py` (open DB pool → load MCP tools → `get_graph()`; on shutdown: `shutdown_scheduler()` → `shutdown_pipelines()` → `browser_manager.shutdown()` → `close_pool()`). The chat graph is a process-wide `@lru_cache` singleton, so adding tools at runtime requires restarting. The **pipeline** graph deliberately does *not* depend on that ordering: it resolves tools by name at run time via `find_tool()`, so it compiles on first use.
  - **What the chat model can actually see is narrower than `all_tools()`** (2026-10-22). `_tools_for_current_run()` in `nodes.py` filters before `bind_tools`: the three raw MCP tools (`get_latest_policies` / `get_policy_facets` / `get_policy_fulltext`) are **never bound to chat** — gov.cn is a built-in source, so `search_policy_library` covers them and the model no longer has two overlapping entries to choose between. They stay in `MCP_TOOLS` for the pipeline and the facets service via `find_tool()`. Browser tools are hidden when no `BrowserRun` is active. ToolNode still executes the full list; only the schemas the model sees are filtered.
- **MCP integration** (`app/agent/mcp.py`): loads **China-Central-Policy-MCP** (State Council policy retrieval: `get_latest_policies` / `get_policy_fulltext` / `get_policy_facets`) via stdio/`node` from the build at `tools/China-Central-Policy-MCP/build/index.js` (default path computed relative to repo root in `app/config.py`, overridable via `MCP_POLICY_*` env vars). That directory is **vendored into this repo as plain source** (originally cloned from the public upstream `guangxiangdebizi/China-Central-Policy-MCP`; `get_policy_facets` and the search fixes are local additions, and upstream updates must now be merged by hand — it is no longer a git submodule). `node_modules/` is ignored; run `npm install` there before `npm run build`. **Editing `src/` requires `npm run build` (= `tsc`)** — the server loads `build/index.js`, so an un-built source change is a silent no-op, and `build/` is committed. Failure degrades gracefully to local tools only — the server still starts. `tool_text()` / `tool_json()` normalise the MCP return shape (str / tuple / content-block list) — reuse them instead of hand-parsing results. `get_policy_fulltext` extracts the body via a container-selector chain (`div#UCAP-CONTENT` → `.pages_content` → `article` → `.content` → `.article`) and **stops there when a container matched** — the whole-page `$("body")` fallback only fires when the page has none of them (unknown layouts): image-only 红头文件 pages have an empty container, and falling through would turn the nav/script/meta page shell into the "body" (2026-10-13 医保发〔2026〕19号 case). It also reports `image_count` (imgs inside the matched container) so the server can label such pages 图片版; server code must tolerate the field's absence (old, un-rebuilt builds don't send it).
  - **gov.cn search quirks** — the condensed rules are in [data-pipeline.md](data-pipeline.md) → *Search & filters*; the **full measured evidence** (filter ↔ parameter table, channel-capability matrix, `gongbao` behaviour) is in [gov-cn-search-quirks.md](gov-cn-search-quirks.md).
- **Ingestion tools** (`app/agent/ingestion_tools.py`, one tool: `ingest_policies`) are the **only** things the agent can do that *store* data. `get_latest_policies` / `get_policy_fulltext` are read-only (they leave nothing behind), `dry_run_ingestion` is a pre-import trial (it says so itself: no task, no result rows), and `manage_ingestion_job(action="run_trial")` can start a run but only for a **registered configured source** (it resolves through the `content_source` table, so the built-in gov.cn is unreachable that way) and it stops at the confirmation gate. Four actions close the loop: `start` / `inspect` / `confirm` / `cancel`. Load-bearing properties:
  - **One implementation, two entry points**: `POST /api/tasks` and `POST /api/tasks/{id}/confirm` now delegate to `app/services/ingestion.py`, the same functions the tool uses, so the confirm sequence (discard unselected → `refresh_task_counts()` → log → set `running` → `start_extraction`) cannot drift between the page and the chat. The routes keep only HTTP semantics, mapping `IngestionNotFound`→404 / `IngestionConflict`→409 / `IngestionRejected`→400.
  - **The same rule now covers cancelling** (Phase 33, batch 2): `POST /api/tasks/{id}/cancel` delegates to `services/ingestion.cancel_ingestion`, so the page's button and the agent's `action="cancel"` run the *same* sequence (cancel the background asyncio task → `finish_task(..., "failed")` → log) and produce the same wording. `ingest_policies` also gained `action="cancel"` — a user saying "算了别抓了" must not be answered by starting *another* crawl.
  - **`inspect` answers three questions the model actually asks**: which task (omitting `task_id` falls back to the most recent one, `repo.fetch_current_task` — a new session has no id in hand), what state it is in, and **why** it looks like that (the task log rows are included; without them a zero-result retrieval or a pile of "不建议入库" verdicts can only be guessed at).
  - **The confirmation gate moves, it does not disappear**: `start` runs only the retrieval phase and always stops at `awaiting_confirmation`; `confirm` refuses unless `user_approved=True` (same spirit as `register_source(approved=...)`). `prompts/chat.md` tells the model to read the candidates out and wait for the user. `wait_for_settled()` polls the task **row** (never the running pipeline) for up to 120 s so a single tool call can return a readable answer; a timeout is reported as "still running", not as an error.
  - **Source names are strict for the model only**: `resolve_source_label(..., strict=True)` refuses unknown names and lists what is available. The pipeline keeps `get_by_label`'s deliberate fallback to the built-in gov.cn source (relied on by `routes/filters.py`, asserted in `scripts/test_sources.py`) — a hallucinated name silently crawling the wrong site is a failure mode only the model produces.
  - **`web_search=true` turns a sentence into an entry URL** (2026-10-23): `start_web_search_ingestion` (`services/ingestion.py`) first checks browser availability, then asks Tavily (`services/websearch.py`, thin httpx client — 0 results / no key / network failure all come back as `{ok:false, error}` in Chinese, never raised) for an **official policy page URL** (`.gov.cn` results always rank above non-official ones; `official=false` is a flag the prompt tells the model to disclose), then hands that URL to `start_ingestion` on the **legacy `任意网站（无头浏览器）` pseudo-source** — the only carrier for "any entry URL" that is not persisted per site, admitted by `start_ingestion`'s explicit key check (`browser_any` lacks the `browser_driven` class marker the scheduler relies on). The rendered config / scheduler paths keep excluding it; only this chat-side flow creates those rows. The confirmation gate is untouched: the task still stops at `awaiting_confirmation`. Configuration: `TAVILY_API_KEY` / `TAVILY_MAX_RESULTS` / `TAVILY_TIMEOUT_SECONDS` (Settings group, restart on change), browser via the usual `BROWSER_ENABLED` + Playwright setup. Smoke test: `uv run python scripts/test_websearch.py` (network only, no DB / browser needed for the first two checks).
  - The task a conversation starts **appears on the 抓取 page** like any other (same rows, same SSE) — that page remains the fallback UI for confirming or cancelling it.
- **Policy-library search** (`app/agent/library_tools.py`, one tool: `search_policy_library`; service `app/services/library_search.py`) is the **read-only** way for the model to look at what the system actually covers. Four actions: `sources` (list the enabled sources with their coverage: level / organization / entrypoints / filter capabilities), `search` (keyword search across the selected sources; `agencies` / `doc_types` map to the sources' own server-side filters), `fulltext` (fetch one document's body), `facets` (which agencies / doc types a source can be filtered by). Load-bearing properties:
  - **It exists because the MCP search tools are gov.cn-only.** `get_latest_policies` / `get_policy_facets` cover the State Council library (national level) and nothing else, so asking them "Zhejiang science policies" and answering "Zhejiang's own files are not in this library" was answering a question nobody asked — the model never checked whether the system had an enabled Zhejiang source. `prompts/chat.md` now encodes the corrected order: `search_policy_library(action="sources")` first, then `action="search"` with `scope` (region / organisation) and `keywords`. Since 2026-10-22 the template also says this is the **only** retrieval entry: the raw MCP tools are no longer bound to chat, so national-level `agencies` / `doc_types` filtering goes through the same action (values discovered with `action="facets"`).
  - **Its date / body semantics are the pipeline's, not a second dialect** (Phase 33, batch 1): `fetch_source_fulltext` cleans the body with `split_fulltext` (meta table, boilerplate and zero-width characters removed), reports `publish_date` **only** when the source declares `fulltext_date_is_publish` — gov.cn's full-text date is the **signed** date, so that path returns `publish_date=null` plus a separate `signed_date` and a `date_note` — and returns `body_ok` / `body_metrics` (the same `pipeline_min_body_chars` / `pipeline_min_sent_enders` thresholds the pipeline uses, so image-only and thin-shell pages are labelled instead of being quoted) together with the attachment list. The search hits report the list-round date as `publish_date` (that round *is* the publish date). The authoritative version is `crawl_graph._preflight_bodies`; this path copies it rather than re-deriving it.
  - **Its search budget is the pipeline's too** (Phase 33, batch 4): per-keyword rows are capped by `pipeline_per_keyword_limit`, the total number of site calls shares one `pipeline_max_search_calls` budget across all sources, and paging continues until a page yields **no new link** (the same "a round with zero new links means paging is broken" rule the pipeline uses — that is what stops a site that ignores its page parameter from looping forever).
  - **Two standing caveats ride along with every search** (Phase 33, batch 4): the read-only path runs **no relevance judgement** (that happens on ingest), and an empty `agency` / `doc_no` means "the list page did not parse it", not "there is no issuing agency". Both are stated in the payload (`caveats`) and in `prompts/chat.md`, because a model that reads an empty field as "absent" will confidently tell a researcher something false.
  - **Read-only by construction**: it searches the adapters directly (`search_plan` → `search` → `validate_item` → `normalize_item`), so it writes **no** task, **no** `policy_document` row and spends **no** extraction tokens. `ingest_policies` remains the only path that stores anything — the two are complementary (look vs. capture), not alternatives.
  - **"Enabled" means the process registry**: `app/sources/registry.py` holds the built-in gov.cn source plus the `status=active` configured sources loaded at startup; the DB is consulted only for display metadata (`level` / `organization`) and degrades quietly when unavailable. The legacy `任意网站（无头浏览器）` pseudo-source is excluded, exactly like in `routes/sources.list_sources`.
  - **Per-source failures never abort the call**: a source that times out or whose adapter throws is reported in that source's `error` field while the other sources still answer. A broken `normalize_item` is recorded too — silently dropping items would read as "no such policies exist", which is a lie the prompt forbids.
  - `in_library` on every hit tells the model whether the document is already in the 成果库 (`repo.fetch_library_urls()`), so it can say "already in the library" instead of re-offering it.
- **Library search** (`app/agent/library_tools.py`, second tool: `search_library`; service `app/services/library_query.py`) is the **inside** counterpart of `search_policy_library`: it reads the 成果库 — the documents that were already crawled, extracted and stored — with `action="list"` (keyword / agency / doc type / year, same filters as the page's 成果库 list) and `action="detail"` (policy metadata + the extracted **facts / info / knowledge** triple + the archived body). It is deliberately a **separate tool**, not another action of the outer search: the two answer different questions ("what is out there" vs "what do we already have"), and merging them is how a model ends up re-crawling what the library already holds. Same repository calls and same schema conversion as `GET /api/policies`, so the two views cannot drift.
- **Three more capabilities landed in Phase 33, batch 3**, each by *lifting the page's logic into a service* so the chat and the page share one implementation:
  - **Facets** (`app/services/facets.py`, reached from the agent through `search_policy_library(action="facets")`): `GET /api/filters/facets` now delegates here. The three branches are unchanged — gov.cn's live MCP facet (returned as-is, even when both lists are empty, so "no results" can be shown), configured sources (agency = column name, no doc types), headless sources (nothing). The tool adds its own wording for the fallback case; the page payload is untouched.
  - **Schedules** (`app/services/schedule.py` + tool `manage_schedule`, `app/agent/schedule_tools.py`): list / create / toggle / run-now / delete. `POST /api/schedules*` now delegates here. **The scheduler auto-confirms and auto-ingests** (it bypasses the chat's confirmation gate — pre-existing design), so the tool's description and `prompts/chat.md` say so explicitly, and the model must confirm the schedule with the user before creating one.
  - **One-shot website import** (`app/agent/onboarding_tools.py`, tool `import_source`): runs the page's six-stage orchestration (`app/services/source_import.py`) end to end and waits for it, returning the acceptance verdict, the failure attribution and the `headless_eligible` hint — plus `action="save_browser"` for the page's "保存为无头浏览器来源" button, which had no agent entry at all. **Since 2026-10-22 this is the default onboarding path** — `prompts/chat.md` and the `website-source-onboarding` Skill both say "one-shot first, manual only on a selector / entry / pagination attribution"; the nine stage tools stay for that fallback and for explicit step-by-step control.
- **Conversation memory**: `InMemorySaver` checkpointer keyed by `thread_id` (request field). Memory is lost on restart; swap for `PostgresSaver` etc. for persistence.
- **Tool-call pairing is enforced before every model call** (`app/agent/history.py`, `sanitize_tool_pairs`, called from `call_model`): OpenAI-compatible gateways — DeepSeek in particular — reject a request whose assistant `tool_calls` lack a matching `ToolMessage` per `tool_call_id` (400 `insufficient tool messages following tool_calls message`). Cancelling a run mid-tools leaves exactly such a half-turn in the checkpointer (LangGraph commits the `agent` superstep before `tools` runs, and a new input does not resume the pending tool tasks), and because the front-end keeps the same `thread_id` after 停止, that thread stays poisoned for every later message. The sanitizer drops unmatched assistant turns and orphan `ToolMessage`s from the **outbound view only** (state is left untouched), logging a warning; it never fabricates a result. `scripts/test_agent_history.py` covers the cases offline.
- **Known gaps / backlog**: the agent's *ingestion* path shares the pipeline's code and therefore inherits every pipeline upgrade, but three things on the agent side do **not** go through the pipeline — the read-only search (`app/services/library_search.py`), the nine stage-by-stage onboarding tools (the page uses the newer six-stage orchestration in `app/services/source_import.py`), and the capabilities the agent simply has no tool for (reading the 成果库, cancelling a task, task logs, schedules, facets). The itemised checklist — with `file:line` evidence, impact and proposed fix for each — is in [../plans/2026-10-21-agent-alignment.md](../plans/2026-10-21-agent-alignment.md) (Phase 33, Chinese). Read it before adding a new agent capability: it records which gaps are already known, so the next one does not get re-discovered.
- **LLM 协议** (`app/agent/nodes.py`): everything speaks the **OpenAI-compatible protocol** via one `ChatOpenAI` path (`_build_llm`) — `OPENAI_API_KEY` is sent as a standard Bearer `Authorization` header by the openai SDK, so there is no x-api-key/Authorization dual-header conflict and no `auth_token` special case anymore. `thinking=True` maps to `reasoning_effort="high"`; omitted = server default.
- **No forced tool_choice** (`app/pipeline/extract.py`): `llm.with_structured_output(...)` forces `tool_choice` naming the schema tool, and some reasoning-model gateways reject "thinking on + forced tool_choice" (historically a hard 400 on Kimi's anthropic endpoint) — `_extract_via_tool()` binds the Pydantic schema as a tool and lets the model choose instead, then falls back to the lenient JSON-text parse. Apply the same rule to any new structured call.
- **SSE streaming** (`app/api/routes/agent.py`): `POST /api/chat/stream` emits `data: {"type": "token", "content": ...}` lines, terminated by `{"type": "done"}` on normal completion; errors are sent as `{"type": "error"}` events in-stream rather than HTTP errors. Every tool call additionally emits `{"type": "tool", "name", "detail", "status": "start|done", "ok"}` events (ordinary tools via `call_tools`, browser tools via the `BrowserRun` emitter — same queue, see the load-bearing note below). Each **chat-model call** also emits `{"type": "usage", "model", "input_tokens", "output_tokens", "cached_tokens", "reasoning_tokens"}` (`app/agent/usage.py`, emitted from `call_model`), so a multi-hop ReAct turn yields one event per model call and the UI sums them; tool-internal model calls are deliberately not reported. `usage` is omitted entirely when the gateway returns no usage block — the UI then shows timing and call counts only, never a guessed number. `_extract_text` filters content blocks to `text` only, skipping thinking/tool blocks — reuse it when handling message content. Three things about this endpoint are load-bearing:
  - **Token frames are filtered by node.** `stream_mode="messages"` yields chunks from *every* chat model in the run, including models called **inside a tool** (page analysis / field extraction in `import_source`, the ingestion service) because LangChain propagates callbacks through the contextvar. Forwarding all of them leaked raw `extract_fields` JSON — `{"publish_date": …, "evidence": …}` — into the user's bubble, and concurrent extraction calls interleaved mid-string. The pump therefore drops any chunk whose metadata `langgraph_node` is not `agent`. Keep that filter if you add another stream mode.
  - It carries the **same three anti-buffering headers** as the other two SSE endpoints (`Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`) and emits a `: ping` comment every 15 s — which genuinely fires here, because a tool call can sit silent for 10–20 s.
  - The heartbeat **cannot** be written as `asyncio.wait_for(agen.__anext__(), 15)`: on timeout that throws `CancelledError` *into* `astream` and kills the graph. Instead `astream` runs in a background task pumping an `asyncio.Queue`, and the timeout applies only to `queue.get()`.
  - `done` is emitted **after** the loop, never from a `finally`. On client disconnect (the user pressed 停止 / closed the tab) the coroutine is cancelled and yielding there would raise `RuntimeError: async generator ignored GeneratorExit`.
  - **Tool events for every tool, from two emitters.** `call_tools` (a wrapper around the prebuilt `ToolNode` in `app/agent/nodes.py`) emits `tool` start/done for ordinary tools (policy-library search, library query, ingestion, onboarding, schedules), keyed by the `chat_emit_var` ContextVar the stream route sets in the same `isolated_context()` as the graph task; without an emitter (non-stream `/api/chat`, pipeline) it degrades to a bare `ToolNode`. Browser actions self-emit richer events from inside the tool functions via the `BrowserRun` emitter, so `call_tools` **skips `browser_*` names to avoid double events** (user decision 2026-10-20: intermediate reasoning text also became replace-per-segment, and superseded segments are kept as `text` steps in the same list — the bubble always shows only the latest segment). The frontend handles `token` / `tool` / `error` / `done` explicitly and **ignores unknown types** — never treat every non-token event as "done".
  - **Browser run lifecycle**: when `browser_runtime.available()` the route creates a `BrowserRun` inside the same `isolated_context()` as the graph task (the contextvar must be set in the Context the tools inherit); unavailable engine simply means no run and no browser tools (no HTTP 400 — nothing was explicitly requested). `recursion_limit` rises to `max(25, 2*(BROWSER_MAX_ACTIONS+4))` whenever the engine is available. On completion/cancel/client disconnect the `finally` cancels the pump then `asyncio.shield(run.aclose())` so the browser context and its concurrency slot are always released.
- **Prompts live in `prompts/`** (repo root), read through `app/prompts.py::load_prompt(name)`. The loader is deliberately uncached (a small file read per call) and **raises** on a missing/empty file rather than falling back to `""` — a silent placeholder was exactly the bug this replaced. When the read happens is the consumer's choice, and that decides whether editing a prompt needs a restart: `nodes.py` reads `chat.md` (and, while browsing, `chat_browser.md`) inside `call_model`, and appends a `今天是 YYYY-MM-DD（以服务器本地时区为准）。` line computed at call time — the `get_current_time` tool was removed 2026-10-22 (no model turn should ever be spent on a clock); the pipeline discovery loop reads `browser_browse.md` per run; `judge.py` reads `judge.md` per call (all hot), while `extract.py` binds `extract` / `extract_json_fallback` / `extract_fields` to module constants (restart needed). `JUDGE_INSTRUCTIONS` still overrides `judge.md`. See `prompts/README.md` for the file table.
- **Observability (Langfuse / Litefuse, self-hosted)** — `app/tracing.py`, Phase 21. Every call site enables it the same way: build the LangGraph config, then `config.update(trace_config(...))`. **`trace_config()` returns `{}` when tracing is off, so call sites never need an `if`.** Wiring: `_chat_config()` in `api/routes/agent.py` (one trace per turn, `session_id = thread_id`, so a conversation groups into one session), `run_pipeline()` in `crawl_graph.py` (one trace per retrieval segment — the MCP tool calls show up as child spans), and `_extract_one()` (**one trace per policy**, tagged `pipeline`/`extract`, `session_id = task-<id>`; deliberately *not* one giant trace per task — the two phases are separated by the confirmation gate and by process fragments). `extract_policy()` takes an optional `config: RunnableConfig` and hands it to `llm.ainvoke` explicitly rather than relying on callback inheritance — that is what keeps the tool attempt and the JSON fallback inside the same trace.
  - **Degradation follows the MCP/judge precedent: observability must never break the product.** `_get_handler()` returns `None` — and every `trace_config()` therefore returns `{}` — when `LANGFUSE_ENABLED=false` (the switch lives in `.env.features`; the keys and URL stay in `.env`), when either key is empty, when the `langfuse` package isn't installed, or when client init raises. One line in the startup log, nothing else changes.
  - **Self-hosted only.** Traces go to `LANGFUSE_BASE_URL`/`LANGFUSE_HOST` (default `http://localhost:3000`); nothing leaves the machine. Pointing that at a cloud endpoint would ship conversations *and* policy full texts to a third party — see the note in `.env.example` / `.env.features.example`.
  - **Env var name is normalised, not assumed**: `langfuse_host` in `config.py` uses `AliasChoices("LANGFUSE_HOST", "LANGFUSE_BASE_URL")` because the SDK docs disagree on the name, and `_export_endpoint()` writes the resolved value under *both* names before init so both "pass it explicitly" and "let the SDK read the env" work.
  - `flush_tracing()` runs at the end of the `lifespan` shutdown — the SDK reports in background batches, so without it the last traces are lost.
  - **Each graph run gets its own OTel context** — `tracing.isolated_context()`, applied wherever the run is launched as a task: `/api/chat`, `/chat/stream`'s `pump()`, and `crawl_graph._track()` all use `asyncio.create_task(..., context=isolated_context())`. Langfuse v5's `CallbackHandler` attaches its root span to the *current* OTel context when a run starts and detaches it when the run ends; LangGraph executes nodes in copied contextvars, so the detach can land in a different context and fail (the SDK deliberately treats that as ignorable). The leaked active span then stays in the long-lived FastAPI process's execution context, and the next request's root span parents onto a span that was never exported — the trace has no real root, `traces_scalar` never collects it, and the UI shows only the first conversation plus `Trace not found` on detail. The helper copies the current context (business contextvars survive) and swaps *only* the OTel contextvar for an empty context. Recognise the symptom as "only the first chat after a server start is recorded" and never launch a graph run without it.
- **Frontend consumer** (`web/src/api/client.ts::streamChat`, `web/src/store/chat.ts`): the chat stream is the **only POST** of the three, and `EventSource` is GET-only, so it is the one SSE consumer that does not go through `subscribeSse` — it hand-frames `data: {...}\n\n` over `fetch` + `response.body.getReader()`, buffering across reads (a frame *will* be split, and a Chinese character's UTF-8 bytes can be too — hence `decode(..., {stream: true})`). The chat store owns that stream at module scope, so navigating away mid-answer does not interrupt it. It also accumulates `usage` events into `lastTurn` / `sessionUsage`; `AgentPage.vue` renders them as the small line under the composer (model, input / cache hit, output / reasoning, model and tool call counts, first-token latency, elapsed time, session totals). Everything shown there is measured — never persisted, and cleared by 「新对话」.
