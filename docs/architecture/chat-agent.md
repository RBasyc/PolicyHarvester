# A. Chat agent (`app/agent/`)

> Part of the [docs wiki](../README.md). Companion pages: [overview.md](overview.md),
> [data-pipeline.md](data-pipeline.md), [source-onboarding.md](source-onboarding.md).

The ReAct graph: `START -> agent --(tool calls)--> tools`, looping until the model stops
calling tools. Key flows that span multiple files:

- **Optional browsing** (`app/browser/`, Phase 24): `ChatRequest.browser_enabled` creates a
  per-request `BrowserRun`, puts it in the `browser_run_var` ContextVar, and the model may call
  `browser_*` tools. `all_tools()` always contains them (ToolNode must be able to execute),
  but `call_model` filters the list before `bind_tools` — without an active run the schemas
  never reach the model. `prompts/chat_browser.md` is appended only in that mode. See
  [browser.md](browser.md) for the security invariants and the worker-loop design; this page
  only covers the chat-side wiring.

- **Tool registration is a two-stage registry** (`app/agent/tools.py`): local `@tool` functions live in `TOOLS`; MCP tools are appended to `MCP_TOOLS` at startup. Both `graph.py` (ToolNode) and `nodes.py` (`bind_tools`) call `all_tools()`, so the chat graph **must be compiled after MCP tools load** — enforced by the FastAPI `lifespan` in `app/main.py` (open DB pool → load MCP tools → `get_graph()`; on shutdown: `shutdown_scheduler()` → `shutdown_pipelines()` → `browser_manager.shutdown()` → `close_pool()`). The chat graph is a process-wide `@lru_cache` singleton, so adding tools at runtime requires restarting. The **pipeline** graph deliberately does *not* depend on that ordering: it resolves tools by name at run time via `find_tool()`, so it compiles on first use.
- **MCP integration** (`app/agent/mcp.py`): loads **China-Central-Policy-MCP** (State Council policy retrieval: `get_latest_policies` / `get_policy_fulltext` / `get_policy_facets`) via stdio/`node` from the build at `tools/China-Central-Policy-MCP/build/index.js` (default path computed relative to repo root in `app/config.py`, overridable via `MCP_POLICY_*` env vars). That directory is **vendored into this repo as plain source** (originally cloned from the public upstream `guangxiangdebizi/China-Central-Policy-MCP`; `get_policy_facets` and the search fixes are local additions, and upstream updates must now be merged by hand — it is no longer a git submodule). `node_modules/` is ignored; run `npm install` there before `npm run build`. **Editing `src/` requires `npm run build` (= `tsc`)** — the server loads `build/index.js`, so an un-built source change is a silent no-op, and `build/` is committed. Failure degrades gracefully to local tools only — the server still starts. `tool_text()` / `tool_json()` normalise the MCP return shape (str / tuple / content-block list) — reuse them instead of hand-parsing results. `get_policy_fulltext` extracts the body via a container-selector chain (`div#UCAP-CONTENT` → `.pages_content` → `article` → `.content` → `.article`) and **stops there when a container matched** — the whole-page `$("body")` fallback only fires when the page has none of them (unknown layouts): image-only 红头文件 pages have an empty container, and falling through would turn the nav/script/meta page shell into the "body" (2026-10-13 医保发〔2026〕19号 case). It also reports `image_count` (imgs inside the matched container) so the server can label such pages 图片版; server code must tolerate the field's absence (old, un-rebuilt builds don't send it).
  - **gov.cn search quirks** — the condensed rules are in [data-pipeline.md](data-pipeline.md) → *Search & filters*; the **full measured evidence** (filter ↔ parameter table, channel-capability matrix, `gongbao` behaviour) is in [gov-cn-search-quirks.md](gov-cn-search-quirks.md).
- **Ingestion tools** (`app/agent/ingestion_tools.py`, one tool: `ingest_policies`) are the **only** things the agent can do that *store* data. `get_latest_policies` / `get_policy_fulltext` are read-only (they leave nothing behind), `dry_run_ingestion` is a pre-import trial (it says so itself: no task, no result rows), and `manage_ingestion_job(action="run_trial")` can start a run but only for a **registered configured source** (it resolves through the `content_source` table, so the built-in gov.cn is unreachable that way) and it stops at the confirmation gate. Three actions close the loop: `start` / `inspect` / `confirm`. Load-bearing properties:
  - **One implementation, two entry points**: `POST /api/tasks` and `POST /api/tasks/{id}/confirm` now delegate to `app/services/ingestion.py`, the same functions the tool uses, so the confirm sequence (discard unselected → `refresh_task_counts()` → log → set `running` → `start_extraction`) cannot drift between the page and the chat. The routes keep only HTTP semantics, mapping `IngestionNotFound`→404 / `IngestionConflict`→409 / `IngestionRejected`→400.
  - **The confirmation gate moves, it does not disappear**: `start` runs only the retrieval phase and always stops at `awaiting_confirmation`; `confirm` refuses unless `user_approved=True` (same spirit as `register_source(approved=...)`). `prompts/chat.md` tells the model to read the candidates out and wait for the user. `wait_for_settled()` polls the task **row** (never the running pipeline) for up to 120 s so a single tool call can return a readable answer; a timeout is reported as "still running", not as an error.
  - **Source names are strict for the model only**: `resolve_source_label(..., strict=True)` refuses unknown names and lists what is available. The pipeline keeps `get_by_label`'s deliberate fallback to the built-in gov.cn source (relied on by `routes/filters.py`, asserted in `scripts/test_sources.py`) — a hallucinated name silently crawling the wrong site is a failure mode only the model produces.
  - The task a conversation starts **appears on the 抓取 page** like any other (same rows, same SSE) — that page remains the fallback UI for confirming or cancelling it.
- **Conversation memory**: `InMemorySaver` checkpointer keyed by `thread_id` (request field). Memory is lost on restart; swap for `PostgresSaver` etc. for persistence.
- **LLM auth quirk** (`app/agent/nodes.py`): `ChatAnthropic` doesn't accept `auth_token`, so Bearer-token gateways are passed via `default_headers={"Authorization": "Bearer ..."}`.
- **No forced tool_choice** (`app/pipeline/extract.py`): the configured gateway (`kimi-for-coding`) always has thinking on, and an Anthropic-compatible API rejects "thinking enabled + `tool_choice` naming a tool" with 400 `tool_choice 'specified' is incompatible with thinking enabled`. That is exactly what `llm.with_structured_output(...)` sends, so it can never succeed here — `_extract_via_tool()` binds the Pydantic schema as a tool and lets the model choose (it does call it; unforced tool calls are fine with thinking), then falls back to the lenient JSON-text parse. `thinking={"type": "disabled"}` is *not* a workaround: the gateway accepts the request but returns 0 tool calls. Apply the same rule to any new structured call on this gateway.
- **SSE streaming** (`app/api/routes/agent.py`): `POST /api/chat/stream` emits `data: {"type": "token", "content": ...}` lines, terminated by `{"type": "done"}` on normal completion; errors are sent as `{"type": "error"}` events in-stream rather than HTTP errors. Every tool call additionally emits `{"type": "tool", "name", "detail", "status": "start|done", "ok"}` events (ordinary tools via `call_tools`, browser tools via the `BrowserRun` emitter — same queue, see the load-bearing note below). `_extract_text` filters content blocks to `text` only, skipping thinking/tool blocks — reuse it when handling message content. Three things about this endpoint are load-bearing:
  - It carries the **same three anti-buffering headers** as the other two SSE endpoints (`Cache-Control: no-cache`, `Connection: keep-alive`, `X-Accel-Buffering: no`) and emits a `: ping` comment every 15 s — which genuinely fires here, because a tool call can sit silent for 10–20 s.
  - The heartbeat **cannot** be written as `asyncio.wait_for(agen.__anext__(), 15)`: on timeout that throws `CancelledError` *into* `astream` and kills the graph. Instead `astream` runs in a background task pumping an `asyncio.Queue`, and the timeout applies only to `queue.get()`.
  - `done` is emitted **after** the loop, never from a `finally`. On client disconnect (the user pressed 停止 / closed the tab) the coroutine is cancelled and yielding there would raise `RuntimeError: async generator ignored GeneratorExit`.
  - **Tool events for every tool, from two emitters.** `call_tools` (a wrapper around the prebuilt `ToolNode` in `app/agent/nodes.py`) emits `tool` start/done for ordinary tools (MCP search, ingestion, onboarding, `get_current_time`), keyed by the `chat_emit_var` ContextVar the stream route sets in the same `isolated_context()` as the graph task; without an emitter (non-stream `/api/chat`, pipeline) it degrades to a bare `ToolNode`. Browser actions self-emit richer events from inside the tool functions via the `BrowserRun` emitter, so `call_tools` **skips `browser_*` names to avoid double events** (user decision 2026-10-20: intermediate reasoning text also became replace-per-segment, and superseded segments are kept as `text` steps in the same list — the bubble always shows only the latest segment). The frontend handles `token` / `tool` / `error` / `done` explicitly and **ignores unknown types** — never treat every non-token event as "done".
  - **Browser run lifecycle**: `browser_enabled` creates a `BrowserRun` inside the same `isolated_context()` as the graph task (the contextvar must be set in the Context the tools inherit). Unavailable engine → **HTTP 400 before streaming** with the install instructions (`BROWSER_ENABLED` / `uv sync --extra browser` / `playwright install chromium`), because once SSE starts the client can only see an `error` event. `recursion_limit` rises to `max(25, 2*(BROWSER_MAX_ACTIONS+4))`. On completion/cancel/client disconnect the `finally` cancels the pump then `asyncio.shield(run.aclose())` so the browser context and its concurrency slot are always released.
- **Prompts live in `prompts/`** (repo root), read through `app/prompts.py::load_prompt(name)`. The loader is deliberately uncached (a small file read per call) and **raises** on a missing/empty file rather than falling back to `""` — a silent placeholder was exactly the bug this replaced. When the read happens is the consumer's choice, and that decides whether editing a prompt needs a restart: `nodes.py` reads `chat.md` (and, while browsing, `chat_browser.md`) inside `call_model`; the pipeline discovery loop reads `browser_browse.md` per run; `judge.py` reads `judge.md` per call (all hot), while `extract.py` binds `extract` / `extract_json_fallback` / `extract_date` to module constants (restart needed). `JUDGE_INSTRUCTIONS` still overrides `judge.md`. See `prompts/README.md` for the file table.
- **Observability (Langfuse / Litefuse, self-hosted)** — `app/tracing.py`, Phase 21. Every call site enables it the same way: build the LangGraph config, then `config.update(trace_config(...))`. **`trace_config()` returns `{}` when tracing is off, so call sites never need an `if`.** Wiring: `_chat_config()` in `api/routes/agent.py` (one trace per turn, `session_id = thread_id`, so a conversation groups into one session), `run_pipeline()` in `crawl_graph.py` (one trace per retrieval segment — the MCP tool calls show up as child spans), and `_extract_one()` (**one trace per policy**, tagged `pipeline`/`extract`, `session_id = task-<id>`; deliberately *not* one giant trace per task — the two phases are separated by the confirmation gate and by process fragments). `extract_policy()` takes an optional `config: RunnableConfig` and hands it to `llm.ainvoke` explicitly rather than relying on callback inheritance — that is what keeps the tool attempt and the JSON fallback inside the same trace.
  - **Degradation follows the MCP/judge precedent: observability must never break the product.** `_get_handler()` returns `None` — and every `trace_config()` therefore returns `{}` — when `LANGFUSE_ENABLED=false`, when either key is empty, when the `langfuse` package isn't installed, or when client init raises. One line in the startup log, nothing else changes.
  - **Self-hosted only.** Traces go to `LANGFUSE_BASE_URL`/`LANGFUSE_HOST` (default `http://localhost:3000`); nothing leaves the machine. Pointing that at a cloud endpoint would ship conversations *and* policy full texts to a third party — see the note in `.env.example`.
  - **Env var name is normalised, not assumed**: `langfuse_host` in `config.py` uses `AliasChoices("LANGFUSE_HOST", "LANGFUSE_BASE_URL")` because the SDK docs disagree on the name, and `_export_endpoint()` writes the resolved value under *both* names before init so both "pass it explicitly" and "let the SDK read the env" work.
  - `flush_tracing()` runs at the end of the `lifespan` shutdown — the SDK reports in background batches, so without it the last traces are lost.
  - **Each graph run gets its own OTel context** — `tracing.isolated_context()`, applied wherever the run is launched as a task: `/api/chat`, `/chat/stream`'s `pump()`, and `crawl_graph._track()` all use `asyncio.create_task(..., context=isolated_context())`. Langfuse v5's `CallbackHandler` attaches its root span to the *current* OTel context when a run starts and detaches it when the run ends; LangGraph executes nodes in copied contextvars, so the detach can land in a different context and fail (the SDK deliberately treats that as ignorable). The leaked active span then stays in the long-lived FastAPI process's execution context, and the next request's root span parents onto a span that was never exported — the trace has no real root, `traces_scalar` never collects it, and the UI shows only the first conversation plus `Trace not found` on detail. The helper copies the current context (business contextvars survive) and swaps *only* the OTel contextvar for an empty context. Recognise the symptom as "only the first chat after a server start is recorded" and never launch a graph run without it.
- **Frontend consumer** (`web/src/api/client.ts::streamChat`, `web/src/store/chat.ts`): the chat stream is the **only POST** of the three, and `EventSource` is GET-only, so it is the one SSE consumer that does not go through `subscribeSse` — it hand-frames `data: {...}\n\n` over `fetch` + `response.body.getReader()`, buffering across reads (a frame *will* be split, and a Chinese character's UTF-8 bytes can be too — hence `decode(..., {stream: true})`). The chat store owns that stream at module scope, so navigating away mid-answer does not interrupt it.
