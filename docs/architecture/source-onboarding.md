# C. 网站来源接入 (`app/sources/`, `app/services/onboarding.py`, the Skill)

> Part of the [docs wiki](../README.md). How "接入一个新网站" works: the config-driven
> source layer, the onboarding service, the agent tools, and the page-level 导入网址 entry.

Goal: **adding a website becomes a configurable, verifiable, traceable task — not a new crawler each time.** Code supplies generic capability (fetching + parsing); the per-site differences live in data.

- **`app/sources/` (the layer)** — `base.py` defines the `PolicySource` contract (`search_plan` / `search` / `validate_item` / `fetch_fulltext` / `normalize_item`), implemented by the built-in `gov_cn.py` **and** by `html_source.py`'s `HtmlListSource` (config-driven, generic). `net.py` is the controlled HTTP client: public http/https only, per-hop redirect revalidation, `allowed_domains` whitelist, robots.txt, per-host throttle, global semaphore, byte cap. `htmlparse.py` is a **stdlib-only** mini-DOM + CSS-subset engine — it rejects pseudo-classes/sibling combinators (`selector_supported` returns why), so any new selector surface must go through it. `config.py` holds `SourceConfig` + `validate_source_config()` (executability: domain boundary, selectors within the supported subset, non-empty body containers) + `config_fingerprint()` (sha256/16 over the fetch-affecting fields only — `notes`/`license_note`/`contact` excluded, so editing prose doesn't mint a version). `registry.py` resolves sources **by label** (that's the FK tasks use) with conflict protection, and `load_configured_from_db()` loads `status=active` rows — the lifespan calls it, degrading to a warning when the DB/tables are missing.
- **`app/services/onboarding.py`** — the onboarding pipeline: recon → discovery → structure analysis → sampling → config generation → **dry run + acceptance** → registration → ops → layered diagnosis. The dry run deliberately calls the **production** `_search_policies` (fan-out budget, pagination, `validate_item`, judge, body preflight all real) with the config temporarily registered, and leaves a `source_onboarding_run` row — do **not** replace it with a shallow ad-hoc check, that would produce a conclusion inconsistent with real ingestion.
- **`app/agent/onboarding_tools.py`** — the 9 agent tools (`inspect_source` / `discover_content` / `analyze_content_structure` / `sample_content` / `generate_source_config` / `dry_run_ingestion` / `register_source` / `manage_ingestion_job` / `diagnose_source`), merged into `TOOLS` in `app/agent/tools.py`. They import service functions **inside** the function body to avoid the import cycle, never raise (failures are `{"ok": false, "error": ...}`), and truncate long payloads with an explicit marker.
- **`app/services/source_import.py` + `app/api/routes/sources.py`** — the **HTTP entry** to the same capabilities (Phase 15, 页面内「导入网址」), for people who don't want to go through the chat. Orchestration lives in the service module (not in `onboarding.py`, whose function signatures are untouched) so production code carries zero risk; the route layer is thin. `source_import` chains `inspect_source` → `discover_content` → `generate_config` → `dry_run_ingestion` → `register_source` and is **deterministic — no LLM**: it takes candidates from the recon report, so the page and the agent reach the same conclusion through the same code — but **not blindly by score** (2026-10-15 修复，用户报「什么都取不到」): the analyzer's candidates are *structural* ("a cluster of same-signature siblings"), which footers/nav/app-download blocks match exactly and are often the *only* candidates on JS-rendered pages, so `_pick_candidate` **fetches each candidate's own sample detail page for real** (same-host samples ranked first by `_rank_candidates` — ordering, not filtering) and accepts the first that yields a body container with a non-shell body (`_SAMPLE_MIN_CJK = 100` CJK + `≥2` sentence-enders, the same 口径 as `sample_content`); every rejected candidate gets a `rejected_reason` in the DTO ("没试" vs "试了不行"), and `job.candidates` is assigned **before** the pick loop so failure paths still show them. Every assembled selector also passes `_usable_selector` first: `analyze.py` hands back `:nth-of-type(n)` selectors ("降权但保留") but the engine's subset has no pseudo-classes, and `validate_source_config` rejects the **entire** config for **one** unusable selector (that was the second half of the same outage) — strip the position pseudo-class when that yields a supported selector, otherwise **leave the field empty and log it**, never invent a substitute. Job state lives **in-process** (`JOBS`: phase / logs / config / candidates / report), progress streams over SSE at `GET /api/sources/import/{job_id}/stream` (same wire format as `/api/tasks/{id}/stream`; the frontend shares one `subscribeSse()` transport), and the durable trail stays in `source_onboarding_run` — a restart only loses the progress bar. Guards that must not be removed: the URL passes `net.check_url` (public http/https, no private/metadata address) **before** a job exists, `allowed_domains` is derived server-side from the URL host (`_host_domains`, never accepted from the page), and two rules keep a failed re-import from silently killing a working source — `_register_after_dry_run` **puts the previous config back** into the in-process registry when a re-import of an `active` source fails (the dry run temporarily registers then unregisters), and `_sync_registry` keeps **only `active`** rows loadable, matching `load_configured_from_db()`'s restart behaviour (a draft must never be usable without a human hitting 启用). `POST /api/sources/{id}/enable` reuses `register_source(approved=True, force=...)` — the same gate as the agent tool; `force` records 未经验收强制启用 in the change note.
- **Page entry，Phase 16 增量**（来源管理独立成页 `/sources`；`SourceModal.vue` 已删除）——同一批能力的三个新面：
  - **批量导入**：`POST /api/sources/import/batch` 把 N 个地址（1–20）逐个入队，**批内不走 5 秒冷却、满了排队而不是 429**。模型是「一个 `batch_id` 关联 N 个**独立** ImportJob」，不是父子作业：每个子作业走完全同一条六阶段流水线、同一个取消接口、同一道验收闸，只是共享 `batch_id`。逐条**立即**给结果（地址非法 → `invalid` 并给原因，不建作业）；`BATCHES` 只是进程内的聚合视图，不落库。聚合进度是**一个** batch-wide SSE：`GET /api/sources/import/batch/{batch_id}/stream`（**必须是 GET**——`EventSource` 不支持 POST），事件 `phase`（整份队列快照，含每条的排队位置 `position`）/ `log`（任一子作业的新日志透传，带 `job_id`）/ `done` / `error`；单条日志仍按需连单作业的 `/import/{job_id}/stream`。队列快照是**裸 dict**（`batch_snapshot()` 要 `json.dumps` 做变更检测），下发前过一遍 `SourceBatchSnapshot.model_validate()`——schema 不校验的话线上字段会和前端 `types.ts` 各自漂移（`gone` 就是这么差点丢的）。
  - **批量导入只落草案，注册交还前端**：批量子作业走 `draft=True`，试运行通过后**不**自动注册（Phase 15 那个 dev 后门只在单条路径生效，批量下会把 N 个 URL 全灌进生产来源表）。语义上「作业级未注册」= 跑完把 `job.registered` 清成 `None`，页面提示「已登记为草案，请到来源列表启用」。**单条导入（旧弹窗路径）行为不变**——`POST /import` 不带 `draft` 字段，默认 False。
  - **`JOBS` 有内存边界**：`_evict_finished_jobs()` 在新作业完成时惰性驱逐最旧的**终态**作业（保留 30 分钟、上限 50 条，running 永不驱逐——驱逐一个在跑的作业会让它的 SSE 断在半路）。`GET /api/sources/import?limit=` 是这份进程内表的倒序快照；被清出后子作业在批快照里标 `gone`，页面引导去看持久留痕。
  - **两个新 HTTP 门，暴露既有 Agent 工具**：`POST /api/sources/{id}/trial`（`manage_source("run_trial")`，真实小批量抓取，**仅 active 可用否则 409**）与 `POST /api/sources/{id}/health`（`manage_source("health")`，只读第 1 页、不产生任务）。另有 `GET /api/sources/runs/recent?limit=&kind=`：跨来源最近接入记录，每来源取最新一条（`repo.list_onboarding_runs` 多取 5×limit 后在 Python 里 `DISTINCT ON (source_key)` 折叠，附带 `source_label`）。三者都是**静态段**，必须注册在 `/{source_id}` 之前。
- **The filtering layer is declared, not assumed** (2026-10-15：用户问「非 gov.cn 的源不适配日期/机构/关键词筛选怎么办」) — a column list page has no search: without more, a keyword is only compared against the titles of the pages already paged through (recall = `max_pages × per-page`) and a date only against the date printed on those pages. Two halves close that gap.
  - **A 检索型入口 is config, not code** — `entrypoints[].search` (`SearchConfig`) declares that the entrypoint *is* the site's own search page, so `keyword_param` / `date_from_param` / `date_to_param` / `fixed_params` (+ `date_format`) are pushed into that page's query string and recall is decided by the site's own index. `build_entry_url()` is the **single dispatch** used by `HtmlListSource.search()` and by every onboarding probe, so "dry run passed" and "ingestion works" cannot drift apart. Disciplines, all mechanical: `url` must be a page **actually fetched and seen to yield items** (never a guessed `/search`), `list_selector` must describe the **result page's own** structure (it usually differs from the column page), and `method=post` forms or `action=None` (JS-built URL) inputs are reported as unsupported rather than half-configured. `keyword_param` is validated on the entry (whitespace-only would build `?%20%20=…` — an address that looks fine and never matches); `date_format` is checked by rendering 2000-01-02 and requiring 2000/01/02 in the output, because `strftime` echoes bad directives instead of raising. No keyword ⇒ that round skips the search entrypoint (an empty search page is not a browsable path). `pagination.kind="none"` ⇒ pages ≥2 return `None` (otherwise page 2 rebuilds `page=2` on a site that ignores it, re-serving page 1 as duplicates and burning the search budget instead of marking the combo exhausted). `validate_item`'s keyword/date re-check stays ON for both kinds of entrypoint — site search engines tokenize, so "matched server-side" ≠ "relevant".
  - **Page import probes it for real** — `source_import._maybe_add_search_entry()` runs only on the fresh-import path, right after `_pick_candidate`, using the GET forms already reported in `search_forms` (`analyze.search_forms()`; no extra fetch to find them). It builds the probe URL with the **same `build_search_url`** as runtime, fetches it, re-analyses the result page, and adopts the entrypoint only if that page's own `list_candidates` really parse into items — the config is never edited by a guess. Declines are logged and distinguishable: no form / `action` null (JS) / POST / host outside `allowed_domains` / fetched but unparseable / probed and got 0 items. The adopted entrypoint is named 站内检索 (suffixed when taken) and `_rebuild_from_candidate` preserves declared search entrypoints across candidate re-runs.
  - **The UI states which layer does the filtering** — `config.capability_summary()` (= `SourceConfig.capabilities()`, also `summary()["filters"]`, exposed on `SourceDTO` as `keyword_server_side` / `date_server_side` / `search_entrypoints`) answers "server or client?" for keyword / date / agency / doc-type. It accepts **raw dicts** as well as models, because legacy `content_source.config` rows may predate the field and the sources list must not 500. `api/routes/filters.py` builds the facet panel from `source.filter_capabilities()` — the `PolicySource` default claims all-server (correct for gov.cn), so **any new engine must override it** — keeps search entrypoints out of the 发布机构 list (they are not agencies), and the crawl page renders `store.sourceFilterNote` so users are told where a filter takes effect instead of assuming the results are complete.
  - **Acceptance keeps the two kinds apart**: 判据 1 「列表发现」 is computed over **column entrypoints only** — a 0-hit search entrypoint must not fail "every column listed items" (the probe word may simply have no matches on that site). Search entrypoints have their own 判据 1b, **hard only when the run used the user's own keywords**, otherwise soft plus an `untested[]` line when it fell back to `SEARCH_PROBE_KEYWORD` ("通知"); `entrypoints[].probe_keyword` records the word actually used. A search entrypoint with no usable keyword is recorded as **not probed**, never as "0 items" — probing a search page without a keyword would yield the false conclusion "this entrypoint is broken". Health checks carry the same distinction (`reachable: None` + why).
- **A generated date selector must vary across samples, or it is dropped** (2026-10-15：用户报「通过其他来源进来的日期不对，一直都是 3 月 20 日」) — a config-driven source gets **no** date from the list round (`entrypoints[].date_selector` is never set by the importer), so `publish_date` is decided entirely by `detail.date_selectors`: a chain scanned off **one** page (`analyze.meta_candidates` — document order, no scoring), where a footer/template date and the article's own date are indistinguishable. Paged through, the template one writes the **same** date into every row of that source (year facet, window re-check and 成果库 ordering all follow it). So `_sample_detail_analysis` now fetches `_DATE_CHECK_SAMPLES = 3` same-column detail pages (the candidate's own sample + siblings picked from its **own** list page, reusing `page_url` + `list_selector` — the very items this config will fetch) and `_verify_date_selectors` **drops** any candidate whose value is identical on *every* sample; it is skipped for candidates already rejected as non-articles, so a footer block costs no extra fetches. The survivors get re-ordered so a `parse_date`-able one first — `_text_of` only ever reads the **first** selector that yields non-empty text, and on chinanews (2026-10-15 实测) `div.left` re-resolved document-wide to `时政`, shadowing `#pubtime_baidu` and losing the date outright. Drops are honest-not-silent: into the job log and `sample_metrics.dropped_selectors`, and `date_selectors` may end up **empty** — a missing date beats a wrong one, which is this project's standing bias. The threshold is deliberately conservative (all three samples must agree): two same-day 通知 in one 栏目 would otherwise lose a **correct** date. When it is inconclusive the dry run says so instead — 判据 6's note and `coverage_limits` gain "抽样 N 篇的发布日期全部相同，疑似取到了页脚/模板元素" when the sampled values are one single value, because a 100% hit rate off a constant is exactly how this bug got accepted.
- **Honesty rules are mechanical, not aspirational**: `register_source(approved=True)` **refuses** unless a passing dry run exists for the **same fingerprint** (unless the user explicitly approved `force=True`, which appends 未经验收强制启用 to the change note); plain registration lands in `draft`; every acceptance report carries `untested[]` and `coverage_limits[]`; and `blocked` (robots/401/403/login/interior address) is kept distinct from `failed` (the config is wrong) — never collapse one into the other.
  - **The credential is looked up by fingerprint across the whole table — never through a window** (2026-10-15：用户报「手动停用的项目无法再次启用」). The list page's 已验收 badge already asked the question table-wide (`repo.list_passing_dry_run_fingerprints`), while the gate asked it only of「该来源最近 20 条记录」(`list_onboarding_runs(…, limit=20)`) — so once a source had been re-imported enough times, the passing run was pushed out of that window and **the same source showed 启用 in the list and 拒绝启用 from the server**, permanently, with no way to fix it short of `force=true`. A verification record is a **fait accompli**（那份配置真的被跑过一次并通过了）: later 勘察/失败试运行 must not expire it. Both consumers now build the query from one predicate, `repositories._PASSING_DRY_RUN_SQL`, and the gate's miss path distinguishes 「配置改过」(report the fingerprint that did pass, which is the `hint` riding in the refusal) from 「压根没跑过」; a partial index on `report->>'fingerprint'` (schema.sql) serves the lookup.
- **Evidence trail**: recon/sampling/dry runs write `source_onboarding_run`; fetched attachments land under `SOURCE_ARTIFACT_DIR` and are registered in `source_artifact` (URL / sha256 / path / discovering page). Originals are **evidence**, AI extraction output is a **fact candidate** — neither is verified knowledge.
- **Schema**: 4 tables (`content_source`, `content_source_revision`, `source_onboarding_run`, `source_artifact`) + 3 enums (`source_level`, `content_source_status`, `onboarding_status`). All `IF NOT EXISTS` / idempotent, so an existing DB only needs `database/init.sh` re-run (no data reset). Status machine: `draft → validated → active`, plus `disabled`.
- **Tests**: `server/scripts/test_source_onboarding.py` (fake site + **real** orchestration: SSRF checks, parsing, judge, acceptance judging all run for real; only the network exit is stubbed). `--db-scratch` auto-creates a throwaway DB, applies `database/schema.sql`, runs the DB cases, then drops it. The suite **self-reports skips** — "跳过 ≠ 通过". Run it after touching `sources/` or `services/onboarding.py`. `server/scripts/test_source_import.py` covers the Phase 15 **page entry** (`services/source_import.py`) offline, reusing that fake-site kit — selector-subset convergence, detail-rule assembly surviving `:nth-of-type`, pre-enqueue URL checks, the outage's own shape (a higher-scoring footer block must not beat the real list), and the auto-probe of a site search form (a GET form whose result page has its **own** list structure gets adopted as 站内检索; POST / JS-built / 0-item result pages are declined with a reason in the log). The kit's fake site grew a **`query_pages`** registry (`add_query`) so a search endpoint dispatches on path with the query string as parameters — like a real one — and a `build_search_site(method=…, result=…)` fixture. The onboarding suite adds the offline URL/`SearchConfig`/`capability_summary` cases plus a dry run over a config with both entrypoint kinds, including the regression "a 0-hit search entrypoint must not fail 判据 1 「列表发现」". Run both after touching `sources/` or `source_import.py`.
- **Reference docs** live in `.claude/skills/website-source-onboarding/references/` (`tool-map.md` = capability/gap/tool-interface list, `config-schema.md` = field tables + a config the suite actually runs, `acceptance-criteria.md` = the hard/soft criteria and their thresholds). **When you change thresholds, criteria or config fields, update those files** — they are a hand-kept mirror, like `web/src/api/types.ts`.
