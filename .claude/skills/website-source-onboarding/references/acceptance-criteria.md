# 接入验收标准

「接入完成」= `dry_run_ingestion` 返回 `status=passed`。**HTTP 200、单篇样本解析成功、
试运行跑起来了——都不算。** 本文把「怎么算通过」写成可执行的标准，每条都在报告里带实测值。

- **实现**：`server/app/services/onboarding.py`（`dry_run_ingestion`）
- **阈值常量**：同文件顶部（改阈值要重启，见文末）
- **判定**：任一**硬判据**不通过 → `status=failed`；全部硬判据通过 → `status=passed`；
  站点/环境根本不允许取数 → `status=blocked`

## 0. 三种结论

| 结论 | 含义 | 后续动作 |
| --- | --- | --- |
| `passed` | 所有硬判据通过 | 可进阶段 6 注册；**软判据的未通过项与未测试项要一并转述** |
| `failed` | 配置或站点结构有问题（可修） | 按失败项改配置 → **重跑**（配置一变指纹就变） |
| `blocked` | **不是配置问题**：robots 禁止 / 401 / 403 / 需要登录 / 内网地址 / 不在白名单 | **停**。不绕过，按第七节流程处理 |

`blocked` 与 `failed` 必须分开报告——把「站点不让抓」写成「配置写错了」会误导用户去改配置。

## 1. 硬判据（任一不过 = `failed`）

| # | 判据 | 阈值 | 实测值 | 不过多半是 |
| --- | --- | --- | --- | --- |
| 1 | **列表发现** | 每个**栏目**入口第 1 页 ≥ 1 条 | 最少 N 条（逐入口列） | 入口 URL 写错，或 `list_selector` 不对 |
| 1b | **站内检索入口** | 检索型入口用关键词探测时第 1 页 ≥ 1 条 | 最少 N 条（`probe_keyword` 一并给出） | `search` 的参数名写错、检索页只认 POST、`list_selector` 不是检索结果页的 |
| 2 | **检索链路产出** | 扇出检索后 ≥ 1 条可用条目 | N 条 | 关键词过滤太严、日期窗口太窄、判别把条目全剔了 |
| 3 | **正文完整性** | 抽样篇数中正文达标比例 ≥ **80%** | `x/y = z%` | 正文容器选择器错、详情页取回失败（看 `details[].error`） |
| 4 | **翻页可用性** | 声明了翻页的入口，第 2 页能取到且**不是第 1 页的重复** | 逐入口说明 | 翻页规则在该站不成立（参数被忽略 / 模板错） |
| 5 | **URL 去重** | 合并结果内重复 URL 数 = 0 | `N 条 / 重复 0` | 入口之间内容重叠、翻页没真的翻 |

判据 1 只覆盖**栏目型**入口。检索型入口（`entrypoints[].search`）单独成判据 1b：

- 探测关键词优先用**本次试运行给的关键词**（用户就是要用这些词抓）——这时判据 1b 是**硬的**；
- 没给关键词时用兜底探测词 `SEARCH_PROBE_KEYWORD`（默认「通知」，`sources/config.py`），
  这时是**软的**：那个词在站点里可能本来就 0 命中，判不了对错，但报告要如实写清用了哪个词，
  并把它记进 `untested`（「未用你实际要抓的关键词跑一遍」）。
- 检索页没有关键词参数时返回空结果页，所以**不能用入口地址本身探测**——那会得出
  「这个入口坏了」的错误结论。报告里 `entrypoints[].probe_keyword` 就是实际用的词。

判据 3 的「正文达标」= 清洗后正文 **CJK 字数 ≥ `detail.min_body_chars`（默认 200）
且句末标点（。！？；）≥ 2**。第一个数字保证有内容，第二个数字保证**是条文而不是导航壳**。

判据 4 只在配置声明了翻页（`pagination.kind != "none"`）时执行；单页配置会记入未测试项。
检索型入口的第 2 页探测会带上同一个探测关键词（没有关键词就没有可翻的第 2 页）。

## 2. 软判据（不通过不判失败，但如实报低）

| # | 判据 | 阈值 | 说明 |
| --- | --- | --- | --- |
| 6 | 详情页日期命中率 | ≥ **60%** | 取不到日期未必是错——该站详情页可能没有固定日期字段。缺日期的条目在时间窗口生效时按 `drop_undated_when_windowed` 决定去留。**命中率高≠取对了**：抽样各篇的日期值**全部相同**时，note 与 `coverage_limits` 会写明「疑似取到了页脚/模板元素」，必须人工核对 `date_selectors`（恒定值 = 假命中，2026-10-15 用户报的「日期一直是 3 月 20 日」就是这么过的验收） |
| 7 | 详情页机构命中率 | ≥ **50%** | 同上，取不到通常是该站没这个字段，需要补 `agency_selectors` |
| 8 | 附件可达性 | 抽查附件可达率 ≥ **80%** | 只验证「能取回」，**不解析 PDF/OFD 正文**。抽查数 = `min(3, SOURCE_MAX_ARTIFACTS_PER_RUN)` |

软判据不通过时**照常注册**，但报告要把 `actual` 原样给出，让用户知道这条链路是弱的。

## 3. 未测试项（`untested`）

「这次没验证什么」必须单独列出来，不能混进「通过」：

- 正文完整性样本 < 3 篇 → 标注「结论为初步」（**提高 `limit` 重跑才能去掉这条**）；
- 配置为单页模式 → 翻页未测试；
- 抽样页面没发现附件 → 附件链路未验证；
- 数据库不可用 → 成果库去重比对未做；
- 检索型入口只用兜底探测词跑过 → 「未用你实际要抓的关键词验证」；
- 配置只有检索型入口（没有栏目列表页）→ 判据 1「列表发现」无入口可探，记入未测试。

## 4. 覆盖范围限制（`coverage_limits`）

每次试运行都会带上的固定说明，**必须转述给用户**：

- 只试抓了 N 篇 / 每个入口前 K 页，**未覆盖全站历史存量**；
- 未验证登录 / 验证码 / 付费墙之后的内容（按接入规范不绕过）；
- 未验证 JS 动态渲染出来的内容（引擎只解析服务端返回的静态 HTML）；
- 抽样页面发现附件时：附件只做可达性与归档验证，未做正文抽取；
- 抽查数 < 发现数时：`抽样页共发现 X 个附件，只抽查了 Y 个（其余未验证）`；
- 抽样里有图片版页面（正文 CJK 极少）→ 提示人工确认该栏目是否以附件为主。

## 5. 报告的五个部分

`dry_run_ingestion` 的返回里，验收结论由这五项共同构成，缺一不可：

| 字段 | 内容 |
| --- | --- |
| `status` | `passed` / `failed` / `blocked` |
| `criteria[]` | 每条判据的 `name` / `threshold` / `actual` / `passed` / `hard` / `note` |
| `details[]` | 逐篇实测：`url`、`body_cjk`、`sentence_enders`、`body_ok`、`date`、`agency`、`doc_no`、`image_count`、`attachments`、`error` |
| `untested[]` | 本轮**未测试**的环节及原因 |
| `coverage_limits[]` | 覆盖范围限制 |

另有 `entrypoints[]`（逐入口条目数 / 取数错误）、`items_found`、`judge_stats`、`attachments_probed[]`。

> `attachments_probed` 与真实探测范围**严格一致**：它列的就是实际发起过探测的那几个附件，
> 不是「发现的前 3 个」。

## 6. 验收与注册的绑定

- `register_source(config_json, approved=true)` **要求**存在**指纹一致**的通过验收
  （`config_fingerprint()`，见 [config-schema.md](config-schema.md) 第 8 节）。
- 无验收记录 / 配置改过 → **拒绝**，错误文案说明要先跑 `dry_run_ingestion`；配置改过时
  文案里会同时点出「该来源最近一次通过的指纹」与当前指纹，好区分该**重跑**还是该**先跑**。
- **凭据是既成事实，不设条数窗口**：按指纹在 `source_onboarding_run` **全表**里找
  （`repositories._PASSING_DRY_RUN_SQL`，单条与批量两处共用这一条判定口径）。同一来源后来
  再勘察/再失败多少次都不该让凭据失效——2026-10-15 用户报的「手动停用的项目无法再次启用」
  就是窗口造成的：列表页徽标按指纹全表找、显示「已验收」，闸门却只看「该来源最近 20 条
  记录」，凭据被挤出窗口后同一个来源两边各说各话（按钮说能启用、点了被拒）。
- 只有用户**明确同意**时才用 `force=true`：放行同时把「（未经验收强制启用，人工拍板）」
  追加进变更说明，历史里留痕。
- 不带 `approved=true` 的注册一律落 `draft`（草案）。

## 7. 测试怎么跑

```bash
cd server
uv run python scripts/test_source_onboarding.py              # 纯离线
uv run python scripts/test_source_onboarding.py --db          # 追加落库用例（需已建表）
uv run python scripts/test_source_onboarding.py --db-scratch  # 自动建临时库跑落库用例，结束即删
uv run python scripts/test_source_onboarding.py --live        # 追加真实站点勘察（联网）
```

覆盖四类场景（对应交付要求里的「正常 / 部分失败 / 无法抓取 / 人工确认」）：

| 场景 | 断言 |
| --- | --- |
| **正常接入** | 勘察 → 取样 → 配置 → 试运行 `passed` → 注册；附件被探测到 |
| **部分失败** | 部分详情页 500 → `failed`，且报告里如实写出取回失败原因 |
| **无法抓取** | 403 → `blocked`，原因点明访问控制并说明不绕过；robots 禁止 → 勘察即受阻 |
| **人工确认** | 无验收记录时拒绝启用；`force` 必须显式传；未确认时注册为 `draft` |
| **工具层** | 9 个工具都返回可解析 JSON；坏输入报错而不抛异常；展示名撞车被拒 |

测试**自报跳过**：`--db` 相关用例在数据库不可用时会 `skip` 并说明原因，
结尾打印「另有 N 项未跑（见上，不计入通过）」——**跳过不等于通过**。

## 8. 阈值怎么改

阈值是 `server/app/services/onboarding.py` 顶部的模块常量，**进程启动时读入**，
改完要**重启服务**才生效：

| 常量 | 默认 | 含义 |
| --- | --- | --- |
| `_MIN_SAMPLES_FOR_BODY` | 3 | 少于这么多篇样本，正文结论标为「初步」 |
| `_BODY_PASS_RATIO` | 0.8 | 正文达标样本占比下限 |
| `_MIN_SENT_ENDERS` | 2 | 句末标点下限（区分「条文」与「导航壳」） |
| `_DATE_HIT_RATIO` | 0.6 | 日期命中率下限（软） |
| `_AGENCY_HIT_RATIO` | 0.5 | 机构命中率下限（软） |
| `_ATTACHMENT_PASS_RATIO` | 0.8 | 附件可达率下限（软） |
| `_MAX_ATTACHMENT_PROBE` | 3 | 附件抽查数**上限**（实际 = `min(3, SOURCE_MAX_ARTIFACTS_PER_RUN)`） |

`detail.min_body_chars` 也可以**按来源**调（默认 200），改它不需要重启——它随配置走。
