# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a two-part demo (plus a `design.pen` design file at the root). Comments and docs are primarily in Chinese.

- `server/` — Python backend: FastAPI + LangGraph, managed with **uv** (Python >= 3.12). Hosts **two independent graphs**: the ReAct chat agent and the deterministic crawl/extract pipeline, plus a psycopg3 data-access layer over the `agent_demo` database.
- `web/` — Vue 3 + TypeScript + Vite frontend, managed with **pnpm**. API-driven (module-level store in `web/src/store.ts`, `fetch` + SSE client in `web/src/api/`); the old mock `web/src/data.ts` has been removed. `web/design-export/` contains the pen.dev design exports the UI was built from. Two-page product with **no vue-router**: `store.view` (`'crawl' | 'library' | 'library-detail'`) switches the crawl page, the 成果库 page (`LibraryPage.vue`), and the policy detail page (`LibraryDetailPage.vue`); the top bar's tab capsule is the only navigation. The 事实/信息/知识 three-column block is the shared `ExtractionColumns.vue`, used by both `DetailDrawer.vue` (crawl page) and the detail page.
- `database/` — PostgreSQL schema/seed scripts (`schema.sql`, `seed.sql`, `init.sh`, `reset.sh`) for the docker container `server-db-1` (port 5433, db `agent_demo`).

The crawl pipeline additionally needs `DATABASE_URL` (default `postgresql://kos:kos@localhost:5433/agent_demo`) and the `server-db-1` container running. There is no lint/test suite configured beyond the smoke scripts above.

## Build & run (do not do this yourself)

The user compiles and runs the project themselves. After writing or changing code:

- **Do NOT** proactively run builds or dev servers (`pnpm build`, `pnpm dev`, `uvicorn`, `python main.py`, `uv sync`, `docker exec ... psql`, etc.).
- **Do NOT** start background/long-running processes to "verify" a change.
- Instead, state what you changed and tell the user what to run and what to expect.
- Quick read-only checks that don't build or start a server are fine when they genuinely help (e.g. a one-off script the user asked for), but prefer describing the verification over performing it.

## Server architecture

The backend exposes **two independent LangGraph graphs** over HTTP plus a database layer:

```
A. Chat (ReAct agent)                 B. Crawl pipeline (deterministic, two stages)
START -> agent --(tool calls)--> tools   stage 1: START -> prepare -> fetch -> (await_confirm | fail) -> END
          ^                    |           stage 2: (user confirms) -> discard unselected -> extract -> summarize -> END
          |------(done)--> END |                        extract: per-policy fulltext -> LLM -> extraction/fact_item
```

### A. Chat agent (`app/agent/`)

Key flows that span multiple files:

- **Tool registration is a two-stage registry** (`app/agent/tools.py`): local `@tool` functions live in `TOOLS`; MCP tools are appended to `MCP_TOOLS` at startup. Both `graph.py` (ToolNode) and `nodes.py` (`bind_tools`) call `all_tools()`, so the chat graph **must be compiled after MCP tools load** — enforced by the FastAPI `lifespan` in `app/main.py` (open DB pool → load MCP tools → `get_graph()`; on shutdown: `shutdown_pipelines()` → `close_pool()`). The chat graph is a process-wide `@lru_cache` singleton, so adding tools at runtime requires restarting. The **pipeline** graph deliberately does *not* depend on that ordering: it resolves tools by name at run time via `find_tool()`, so it compiles on first use.
- **MCP integration** (`app/agent/mcp.py`): loads **China-Central-Policy-MCP** (State Council policy retrieval: `get_latest_policies` / `get_policy_fulltext` / `get_policy_facets`) via stdio/`node` from the build at `tools/China-Central-Policy-MCP/build/index.js` (default path computed relative to repo root in `app/config.py`, overridable via `MCP_POLICY_*` env vars). That directory is **vendored into this repo as plain source** (originally cloned from the public upstream `guangxiangdebizi/China-Central-Policy-MCP`; `get_policy_facets` and the search fixes are local additions, and upstream updates must now be merged by hand — it is no longer a git submodule). `node_modules/` is ignored; run `npm install` there before `npm run build`. **Editing `src/` requires `npm run build` (= `tsc`)** — the server loads `build/index.js`, so an un-built source change is a silent no-op, and `build/` is committed. Failure degrades gracefully to local tools only — the server still starts. `tool_text()` / `tool_json()` normalise the MCP return shape (str / tuple / content-block list) — reuse them instead of hand-parsing results. `get_policy_fulltext` extracts the body via a container-selector chain (`div#UCAP-CONTENT` → `.pages_content` → `article` → `.content` → `.article`) and **stops there when a container matched** — the whole-page `$("body")` fallback only fires when the page has none of them (unknown layouts): image-only 红头文件 pages have an empty container, and falling through would turn the nav/script/meta page shell into the "body" (2026-10-13 医保发〔2026〕19号 case). It also reports `image_count` (imgs inside the matched container) so the server can label such pages 图片版; server code must tolerate the field's absence (old, un-rebuilt builds don't send it). ### B. Data layer & crawl pipeline (`app/db/`, `app/pipeline/`)

- **Pool** (`app/db/pool.py`): one process-wide psycopg3 `AsyncConnectionPool` (`dict_row`, `autocommit=True`). `open_pool()` warns rather than raising if the DB is unreachable, so the server still boots. `get_pool()` / `close_pool()` are wired into the lifespan.
- **psycopg3 placeholder quirks** (`app/db/repositories.py`): only `%s`/`%b`/`%t` placeholders — **`%(name)s` pyformat raises `ProgrammingError`**, and any literal `%` in the SQL text (e.g. `LIKE '国办发%'`) breaks client-side binding too (`got '%''`). Use positional `%s` + tuples, and prefer `starts_with()` over prefix-LIKE.
- **Repositories** (`app/db/repositories.py`): *all* SQL lives here, parameterized. Two rules matter:
  - **Counters are derived, never incremented.** `refresh_task_counts()` recomputes `crawl_task.total/fetched/extracted/failed_count` from an aggregate over `policy_document`/`extraction` (`UPDATE ... FROM (SELECT ...)`). The progress panel reads `crawl_task` while the result table reads the `v_policy_results` view — recomputation is what keeps those two views from drifting apart.
  - Multi-step writes (e.g. reset extraction + delete facts) go in a single `conn.transaction()`.
- **Pipeline** (`app/pipeline/crawl_graph.py`): the deterministic pipeline, split into **two stages by a human confirmation gate**. Stage 1 (graph A) runs `prepare` → `fetch` → `await_confirm` and **ends**; MCP failure or 0 results routes to `fail` with the design's Chinese error copy. `POST /api/tasks` persists the task then calls `start_pipeline(task_id)` (fire-and-forget asyncio task). The task then sits in `awaiting_confirmation` (non-terminal — SSE stays open, `progress` is 50) until `POST /api/tasks/{id}/confirm` drops the unchecked rows and calls `start_extraction(task_id)`, which runs stage 2: `extract` (semaphore-bounded `asyncio.gather` over `_extract_one`) → `summarize`. **Why two stages**: the graph has no checkpointer (`builder.compile()` with no saver) so `PipelineState` cannot survive a pause — instead the fetched rows live in `policy_document` and `run_extraction_phase()` re-reads them and calls `extract_node`/`summarize_node` directly (they are plain `dict → dict` async functions). `pipeline_extract_concurrency` defaults to 1 so the "第 N/M 篇" stage text stays truthful.
- **Search & filters** (`_search_policies` in the same file): fans out over the `keyword × agency × doc_type` cartesian product under a **total call budget** of `pipeline_max_search_calls` (pagination rounds count too) because the API **silently ignores repeated filter params**. Filters persist as `crawl_task.agencies` / `doc_types` columns (the two-stage graph rebuilds `PipelineState` from the DB row, so filters must be persisted). `_search_policies` applies **client-side re-verification** — drop items whose title lacks the keyword, whose date falls outside `[date_from, date_to]`, and any `gongbao` row when a filter is active — because the API silently returns the full unfiltered browse list on a 0-match strict query. Results are deduped by `url` and capped by `pipeline_max_policies`. **Phase 13 additions**: a `page` param on the MCP tool (gov.cn `p`; the request's `n` is set to `limit` — not the old fixed 100 — so consecutive pages advance exactly `limit` rows; the old fixed-`n` + post-slice combo silently skipped rows `limit+1..100` between pages; requires `npm run build` in the vendored repo) plus a rounds loop — keep paging each combo until `target_new` items **not in the library and not judge-tagged** are collected (judging runs **per page inside the loop**, so 不建议入库 rows never eat the quota) / budget runs out / every combo returns 0 items / a whole round contributes **nothing to the merged result at all** (all-seen repeats = broken pagination, or exhaustion; in-library items *do* count as contributions — a re-run whose first page is entirely in-library keeps paging for new items, which is the whole point of 续抓); `target_new=None` = exactly one round = legacy behaviour (judging still runs — the tags feed fetch_node/scheduler). `fetch_node` partitions results three ways, each capped at cap (`repo.fetch_library_urls()`, global across tasks): 建议入库 new rows fill the quota; judge-tagged and in-library rows are **still inserted** so the confirm panel can gray them out — both groups sink to the bottom (rank order 建议入库 → 不建议入库 → 已在库, matching the stage text), unchecked by default but still manually checkable. **Ingest judge** (`app/pipeline/judge.py`, httpx): posts **仅标题** as `state` to the `/v1/systemone` choice API — 双轴矩阵实测 (2026-10-13, `scripts/test_judge.py`): 机关/文号进 state 会带偏该 RL 模型（文号含「函」直接被判不入库、长多机关标题全灭），「疑问句+枚举」提示词 × 仅标题 = 8/9 且唯一误判方向安全（函被判入库，面板里多一行而已）. Verdicts are stashed on the item (`judge_tagged`/`judge_prob`), flow into `policy_document` via `_to_policy_row`, and land in the `judge_stats` out-param for the fail-open log line. Scheduled flow auto-drops tagged rows straight from the stashed tags (its cursor advances only when `cap` kept rows were found); service down = **fail-open** (keep all, count as recommended, warn). **Body preflight** (same loop, right after the judge; `_preflight_bodies` in the same file): candidates the judge keeps get their fulltext fetched (concurrency `pipeline_preflight_concurrency`) and scored by `fulltext_clean.body_metrics` — cleaned-body CJK chars + sentence-enders (。！？；). Below `pipeline_min_body_chars`/`pipeline_min_sent_enders` (both ≤0 = off, restart to change) → same `judge_tagged` channel, `judge_reason` in-memory for logs (fetch_node splits the log line into laya/body/preflight-fail counts). This is the second screen the title-only judge cannot provide (2026-10-13 两类漏网：图片版文件 body 是整页 CSS/JS 壳——cjk 可达 555 但句末为 0，5% 清洗安全网反而保住垃圾；「现将《方案》印发给你们」式薄壳通知百余字 1 句). Thresholds calibrated by `scripts/test_ingest_filter.py` against real MCP links (好例 cjk≥1062/句末≥29, 坏例句末≤1 — the gap is huge); a preflight fetch failure counts as rejected (tagged, own counter), per «抓不到正文 = 不该入库» — manual tasks still show the row grayed & checkable, scheduled runs drop it via the existing path. The **decision lives at search time on purpose** — extraction adds no ingest judgment (user directive), its `len(body) < 50` check stays a mere fetch-failure guard.
- **Confirmation state**: `task_status` has a fifth value `awaiting_confirmation`; `schema.sql` carries an idempotent `ALTER TYPE task_status ADD VALUE IF NOT EXISTS ...` so an existing DB only needs `database/init.sh` re-run (no data reset). `fail_stale_tasks()` deliberately sweeps only `pending`/`running`, so a task parked at the gate survives a restart and can still be confirmed.
- **Extraction** (`app/pipeline/extract.py`): `extract_policy()` truncates the body to `pipeline_max_body_chars`, tries a structured tool call (`_extract_via_tool`, deliberately **without** a forced `tool_choice` — see the thinking quirk above), and falls back to a lenient JSON parse. Output is 事实/信息/知识 (facts / info{summary,points} / knowledge{concepts,fields,extension}).
- **Business API** (`app/api/routes/tasks.py`, `policies.py`): `POST /api/tasks`, `POST /api/tasks/{id}/confirm` (409 unless `awaiting_confirmation`; 400 if nothing is selected), `GET /api/tasks/current|{id}|{id}/logs|{id}/policies`, `GET|POST /api/policies/{id}/extraction|retry|reextract`, `GET /api/config/pipeline` (read-only view of the effective `PIPELINE_*` defaults), and `GET /api/tasks/{id}/stream` (SSE). The stream replays all logs from id 0 then tails; it emits `task` / `log` / `done` / `error` events, polls every 0.6 s, and sends `: ping` heartbeats every 15 s. `retry` (failed only, else 409) and `reextract` both re-enter `run_single_extraction`.
- **成果库（library）** (`GET /api/policies[/meta][/{id}]`, also in `policies.py`): the cross-task results library — only `extracted` rows, **deduped by `source_url`** (`DISTINCT ON`, latest task's row wins) so re-running a task never duplicates/overwrites; list supports `keyword` (ILIKE) / `agency` / `doc_type` (derived from `doc_no` prefix: 国办发/国办函 before 国发/国函, then 国令) / `year` filters + pagination (default 6/page, fixed `publish_date DESC`); `meta` returns header stats (total / distinct agencies / this-month) + facet options; `/{id}` returns meta + three-column extraction + archived `fulltext`. Route order matters: `/meta` and the list route are registered **before** `/{policy_id}` or "meta" gets swallowed as an id. `policy_document.fulltext` is archived by `update_policy_from_fulltext` during extraction (empty body never overwrites the archive); rows predating the column are simply `null` and the UI shows a friendly empty state.
- **Cancellation & clearing** (same route file + `app/pipeline/crawl_graph.py`): background tasks are registered per `task_id` in `crawl_graph._running` (`_track()`), so `cancel_pipeline()` / `cancel_all_pipelines()` can target one task. `POST /api/tasks/{id}/cancel` stops the pipeline and lands the task in `failed` with stage `任务已手动终止` (reusing the existing enum — no `schema.sql` change); `DELETE /api/tasks/{id}` deletes one task and `DELETE /api/tasks` clears all of them, both cancelling first because everything cascades via FKs. A manual cancel deliberately overwrites the `服务重启导致任务中断…` stage that `run_pipeline`'s `CancelledError` branch writes, so the cancel must *await* the cancellation before writing its own state. On startup the `lifespan` runs `repo.fail_stale_tasks()` to fail `pending`/`running` rows orphaned by a killed process (otherwise the UI shows "运行中" forever).
- **Scheduled ingestion** (`app/scheduler.py` + `app/api/routes/schedules.py`, Phase 11): `schedule_job` rows (config snapshot + schedule params + a sliding `cursor_before`) are polled by a 15 s in-process loop (`start_scheduler()` in the `lifespan`, after `get_graph()`; `shutdown_scheduler()` before `shutdown_pipelines()`). A triggered run **skips the human-confirmation gate entirely** — it searches, keeps everything (minus judge-tagged rows, which are dropped with a log line), and calls `run_extraction_phase()` directly. Two mechanics keep repeat runs honest: **cross-run + global-library URL dedup** (`_search_policies(exclude_urls=…)` = this job's history ∪ `fetch_library_urls()` (all tasks' extracted URLs), so a doc ingested by another job/manual task is never re-extracted; empty-after-dedup records `last_status='noop'`, not a failure) and the **sliding cursor** — a full run (hit `pipeline_max_policies`) advances `cursor_before` to *oldest fetched publish_date − 1 day* so the next run backfills older docs; a non-full run means the window is exhausted, so the cursor resets to NULL and the next run chases new docs over `[date_from, today]`. Schedule kinds: `minutely`/`hourly` (`interval_minutes`) + `daily`/`weekly` (`run_time`, `run_weekday` 0=Mon per Python `weekday()`); daily/weekly times are server-local. APIs: `GET|POST /api/schedules`, `POST /api/schedules/{id}/toggle|run`, `DELETE /api/schedules/{id}`. Triggered tasks carry `crawl_task.schedule_job_id` (`ON DELETE SET NULL`). **Re-entrancy (Phase 13)**: the loop is claim-first + serially awaited, so scheduler-triggered rounds of the same job never overlap (a round slower than its interval just fires again immediately after finishing — catch-up without pile-up); the real gap was the manual 「立即运行」 spawning an independent task, now guarded by an in-process `_running_jobs` set (the route returns **409** while a round is in flight; the guard is the TOCTOU backstop inside `run_schedule_job`, which is split into `_run_schedule_job_locked` so early returns can't leak the guard entry).
- **Config** (`app/config.py`): `pydantic-settings` reads the **repo-root** `.env` (path resolved from `__file__`, so CWD doesn't matter), and `load_dotenv()` is also called explicitly because the `anthropic` SDK reads `ANTHROPIC_*` straight from the environment. Pipeline knobs: `DATABASE_URL`, `DB_POOL_*`, `PIPELINE_MAX_POLICIES`, `PIPELINE_PER_KEYWORD_LIMIT`, `PIPELINE_MAX_SEARCH_CALLS`, `PIPELINE_EXTRACT_CONCURRENCY`, `PIPELINE_MAX_BODY_CHARS`, `PIPELINE_MCP_TIMEOUT`. Five of these plus the **extraction model** can be **overridden per task** from the page's collapsed 高级设置 section (values persist on `crawl_task.pipeline_*` columns; NULL = use the global default) — the second extraction stage re-reads them from the task row, so they must be persisted, not just passed in the create request. The model list itself comes from `.env`'s `PIPELINE_MODELS` JSON registry (Phase 12), **hot-read on every access** — `get_model_registry()` → `_live_env()` resolves real-shell-env > current `.env` file > boot-loaded `os.environ` (a snapshot `_REAL_ENV` taken *before* `load_dotenv`, because `load_dotenv` pollutes `os.environ` with file values) — so editing `.env` takes effect on the next request/creation/extraction **without a restart** (keys via `resolve_model_api_key()` too); the frontend refetches `/api/config/pipeline` when the 高级设置 panel opens and snaps a selection that vanished from the registry back to `default_model`. All entries speak the **Anthropic-compatible protocol** (one `ChatAnthropic` path in `_build_llm`): an entry without `base_url`/`api_key_env` reuses the `ANTHROPIC_*` gateway (Kimi Bearer header); DeepSeek entries set `base_url=https://api.deepseek.com/anthropic` + `api_key_env=DEEPSEEK_API_KEY` (standard `x-api-key`; no `langchain-openai` needed). Entries default to `thinking: false` — extraction builds the LLM with `thinking={"type": "disabled"}`; the chat agent is unaffected (it calls `_build_llm()` with no overrides, thinking param omitted). If the kimi gateway returns 0 tool calls under thinking-disabled, the JSON-text fallback still covers it. `get_model_registry()` degrades to a single-model list on parse failure; `crawl_task.pipeline_model` stores the **id**, `extraction.model` records the **actual model name** used. A stale id at run time falls back to the first entry (default) with a warning instead of failing.

### Error contract

All HTTP errors are `{"detail": "<string>"}` — a `RequestValidationError` handler flattens FastAPI's default 422 error list into one string, so clients can render `detail` directly (the frontend's `ApiError` does exactly this).

## Extending the agent

- New local tool: add a `@tool` function in `app/agent/tools.py` and append it to `TOOLS` — no graph changes needed.
- New graph behavior (interrupts, conditional routing): edit `app/agent/graph.py`.
- New state fields: `app/agent/state.py` (use reducers like `add_messages` for mergeable fields).

## Extending the crawl pipeline

- New pipeline stage: add a node in `app/pipeline/crawl_graph.py` and wire the edges (and `_route_after_fetch` if it branches).
- New persisted field: add it to `database/schema.sql`, mirror it in `app/db/repositories.py`, and expose it in the matching `app/schemas/*.py` DTO **and** `web/src/api/types.ts` — the frontend types are a hand-kept mirror, nothing generates them.
- Any write that changes `policy_document`/`extraction` rows must be followed by `refresh_task_counts()` so the derived counters stay honest.
